Shape a proposed Feature through the coupled Blueprint workflow and, only after accepted delivery planning, return its current Atlas handoff.

$ARGUMENTS

## Compatibility Boundary

`/shape-feature` is a compatibility entry point into `blueprint`; it does not invoke a separate Route phase or independently create, accept, or publish a Feature/Map/Work Item graph.

Read `blueprint` and its runtime support files. Use its coupled design and routeability lenses to reconcile the accepted Frame boundary, terrain, Design/RFC Case, disposable evidence, and vertical delivery route. Read `feature-atlas` only when forming its non-authoritative draft handoff candidate or materializing an accepted current delivery plan.

If behavior is unsettled, return to `frame`. If an exact current `HandoffReady` or admissible `HandoffWithLimitations` already exists, use `software-implementation` in explicit `atlas` mode under separately stated implementation/effect authority. Do not use this command to invent missing behavior, architecture, ownership, contracts, acceptance, or implementation authority.

## Required Boundary

Before acceptance, Blueprint may form only the draft candidate defined by `blueprint/contracts/atlas-handoff.md`; it must name every missing owner, decision, acceptance, and evidence item as a blocker and has no Atlas authority. A route-selected Design/RFC Case forbids production source edits.

Only an accepted fresh-worker-executable Production Design RFC and its current accepted Atlas plan may make production work dispatchable. Atlas remains the sole durable delivery-plan authority. A complete current typed Atlas handoff may enter `software-implementation` only in explicit `atlas` mode with separately stated implementation, effect, PR, merge, deployment, and landing authority. Summaries, historical or conflicted plans, draft candidates, and omitted authority remain refused.
